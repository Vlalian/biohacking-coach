# Run AFK

Find the work that genuinely does not need Mads, get his go-ahead once, then build it while he is gone.

The whole value is in the filter. A queue that stalls at 3am waiting for a signup is worse than an empty queue, because an empty queue tells him the truth immediately. **Be ruthless.** When unsure, kick it to "needs you".

See `.agents/skills/run-afk/AFK-SAFETY.md` for the full filter rubric and worked examples.

## The tracker

Issues are markdown at `.scratch/<effort>/issues/NN-name.md`; `PRD.md` / `MAP.md` is the effort parent.

- **`Status:`** — `needs-triage` | `needs-info` | `ready-for-agent` | `ready-for-human` | `wontfix` | `done`. `done` is terminal in practice though `/triage` doesn't document it. Prose follows the token (`done (2026-07-15) — note: ...`) — match the **leading token only**.
- **`Label:`** — `wayfinder:task` | `wayfinder:grilling` | `wayfinder:research` | `wayfinder:map`.
- **`## Blocked by`**, **`## Acceptance criteria`**, **`## Comments`**.

Only files under `issues/` are tasks. A `PRD.md` may say `Status: ready-for-agent` — that's the effort, not a unit of work. Never queue one.

## Workflow

### 1. Scan
Bare `/run-afk` sweeps all `.scratch/`. An argument narrows it: `/run-afk eval-mvp-build`. Collect `issues/*.md` with Status token `ready-for-agent` — that's the candidate pool, not the queue.

### 2. Filter
Re-verify every candidate yourself. `ready-for-agent` is triage's opinion that the spec is *clear* — it was never asked whether a human is *needed*. Hard exclusions:

1. **`Label: wayfinder:grilling`** — a grilling session is a conversation with Mads. Never AFK-safe. (`wayfinder:research` only if the deliverable is a document, not a decision; `wayfinder:map` is planning, so no.)
2. **Unresolved `## Blocked by`** — blocker's Status token must be `done`. Follow chains **transitively**.
3. **Needs Mads's hands or judgment** — signups, credentials, keys, billing, open decisions, expert answers, real-world acts. Often marked `HITL:`; its absence proves nothing. Read for it, don't grep for it.
4. **Too thin for a test list** — if the acceptance criteria won't yield a `/tdd` behavior list, an agent will guess. No criteria, no queue.

Survivors → queue. Everything else → **needs you**, with its one-line reason.

### 3. Present and wait
Show the queue (ranked, dependency order) and the needs-you list. Say how many agents and which branches. Then stop and wait for an explicit go.

**Empty queue → say so and stop.** Name the cork — the one thing that unblocks the most work. Don't scrape the barrel to justify a run.

### 4. Run
One background agent per task, each with `isolation: 'worktree'` — parallel agents on one working tree collide. Only unblocked tasks, so nobody builds on unmerged work. Give each agent the issue, its criteria, and the effort's PRD/MAP.

### 5. Done bar — all three
- `npm test` green.
- Every acceptance criterion **individually** evidenced — walk the list, state what proves each. Not "tests pass, so probably".
- `/code-review` run on the branch, findings fixed in **one** bounded pass, re-verified. One pass, not a loop.

Anything unmet or still open = **incomplete**. Report it, leave work on the branch, don't dress it up.

Agents build via `/tdd`. Its "get user approval on the plan" gate is **already satisfied by the triaged issue** — the acceptance criteria and key interfaces are what Mads signed off. Derive the behavior list and proceed red-green without stopping.

### 6. Land
One branch per task: `afk/<effort>-<NN>-<slug>`. Commit. **Never push, never open PRs.**

### 7. Write back
Update the `Status:` token and append under `## Comments`:

```markdown
> *This was generated by AI during an AFK run.*

**Branch:** `afk/eval-mvp-build-04-calendar-renders-real-sessions`
**Outcome:** done | incomplete
What landed, which criteria are met, what's still open.
```

`Status: done (YYYY-MM-DD)` on success — get the date from `date +%F`, don't guess. Leave Status untouched on incomplete and say why.

### 8. Report
What landed, what failed, what needs Mads — lead with what needs him. That's what he came back for.

## Never

- Never queue a task with a human gate in the middle to "get it started". It stalls, and a stalled agent is invisible until morning.
- Never push or open PRs.
- Never mark `done` on an unevidenced criterion.
- Never treat `ready-for-agent` as sufficient on its own. Re-verify. That's the job.
