# Run AFK

Find the work that genuinely does not need Mads, get his go-ahead once, then build it while he is gone.

The whole value is in the filter. A queue that stalls at 3am waiting for a signup is worse than an empty queue, because an empty queue tells him the truth immediately. **Be ruthless about what counts as AFK-safe.** When unsure, kick it to "needs you".

## The tracker

Issues are markdown under `.scratch/<effort>/issues/NN-name.md`, with `PRD.md` or `MAP.md` as the effort's parent.

- **`Status:`** — `needs-triage` | `needs-info` | `ready-for-agent` | `ready-for-human` | `wontfix` | `done`. `done` is the terminal state in practice even though `/triage` doesn't document it. Status lines carry freeform prose after the token (`done (2026-07-15) — note: ...`), so match the **leading token only**.
- **`Label:`** — `wayfinder:task` | `wayfinder:grilling` | `wayfinder:research` | `wayfinder:map`. This is a hard gate, see below.
- **`## Blocked by`** — links to other issues, or `None`.
- **`## Acceptance criteria`** — the contract. No criteria, no queue.
- **`## Comments`** — where writeback goes.

Only files under `issues/` are tasks. A `PRD.md` may carry `Status: ready-for-agent` — that describes the effort, not a unit of work. Never queue one.

## Workflow

### 1. Scan

Bare `/run-afk` sweeps all of `.scratch/`. An argument narrows it: `/run-afk eval-mvp-build`.

Collect every `issues/*.md` whose Status token is `ready-for-agent`. That's the candidate pool — not the queue.

### 2. Filter — the part that matters

Re-verify every candidate yourself. `ready-for-agent` is triage's opinion, formed before this run; it is a starting point, not a verdict. Read the full issue and apply the rubric in [AFK-SAFETY.md](AFK-SAFETY.md).

Hard exclusions, in order:

1. **`Label: wayfinder:grilling`** — a grilling session *is* a conversation with Mads. Never AFK-safe.
2. **Unresolved `## Blocked by`** — the blocker's Status token must be `done`. Follow chains transitively: a task whose blocker is blocked is blocked.
3. **Anything needing Mads's hands or judgment** — signups, credentials, accounts, API keys, billing, an open decision, a domain-expert answer. Usually flagged in the notes as `HITL:`, but not always. Read for it, don't grep for it.
4. **Too thin to derive a test list from** — if the acceptance criteria won't yield a `/tdd` behavior list, an agent will guess. Guessing AFK is how you come back to confident nonsense.

Everything surviving all four goes in the queue. Everything else goes on the **needs you** list, with the one-line reason.

### 3. Present and wait

Show two lists: the queue (ranked, dependency order) and needs-you (each with its reason). Then stop and wait for an explicit go.

Say plainly what the run will cost and touch: how many agents, which branches.

**If the queue is empty, say so and stop.** Name the cork — the specific thing that would unblock the most work. Do not scrape the barrel for marginal work to justify a run.

### 4. Run

One background agent per queued task, each with `isolation: 'worktree'` — parallel agents on one working tree collide. Queue only unblocked tasks, so no agent ever builds on another's unmerged branch.

Give each agent: the issue's full text, its acceptance criteria, the effort's PRD/MAP for context, and the done bar below.

### 5. The done bar

A task is **done** only when all three hold:

- `npm test` is green.
- Every acceptance criterion is individually evidenced — walk the list, state what proves each one. Not "tests pass, so probably".
- `/code-review` has run on the branch, findings fixed in **one** bounded pass, then re-verified. One pass, not a loop.

Anything unmet, or any finding still open, means **incomplete**. Report it, leave the work on the branch, don't dress it up as done.

Agents build via `/tdd`. Its planning step asks for user approval — **the triaged issue is that approval**. The acceptance criteria and key interfaces are what Mads signed off at triage. Derive the behavior list from them and proceed red-green without stopping. If the issue can't yield that list, the filter should have caught it in step 2; kick it back rather than invent one.

### 6. Land

One branch per task. Commit. **Do not push, do not open PRs** — Mads reviews and merges when he's back.

Name branches after the issue: `afk/<effort>-<NN>-<slug>`.

### 7. Write back

On each finished issue, update the `Status:` token and append under `## Comments`:

```markdown
> *This was generated by AI during an AFK run.*

**Branch:** `afk/eval-mvp-build-04-calendar-renders-real-sessions`
**Outcome:** done | incomplete
What landed, which criteria are met, what's still open.
```

`Status: done (YYYY-MM-DD)` on success — get the date from `date +%F`, don't guess it. Leave Status untouched on incomplete and say why in the comment.

### 8. Report

What landed, what failed, what needs Mads. Lead with what needs him — that's what he came back for.

## Never

- Never queue a task to "get it started" when a human gate sits in the middle. It will stall, and a stalled agent is invisible until morning.
- Never push or open PRs.
- Never mark `done` on an unevidenced criterion.
- Never treat `ready-for-agent` as sufficient on its own. Re-verify. That's the job.
